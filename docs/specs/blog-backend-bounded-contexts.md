# 博客后端六个限界上下文重构规格

> 状态：已发布至 GitHub [Issue #1](https://github.com/Tlfff/ai-blog/issues/1)
>
> 建议标签：`ready-for-agent`
>
> 行为基线：`backend/功能文档.md`（截至 2026 年 9 月 3 日）

## 问题陈述

现有后端仍以 `book`、`helloworld` 示例代码为主，但功能文档已经描述完整的博客业务能力。若直接按接口逐个堆叠实现，用户、文章、评论、点赞、通知和搜索之间会共享模型、数据库访问和业务规则，最终形成难以独立测试、演进和拆分的“大泥球”。

需要在保留既有外部契约与业务效果的前提下，将博客后端构建为一个单体部署、六个限界上下文协作的系统，并把跨上下文统计与通知设计为可靠的事件链路，把搜索同步设计为可独立运行和恢复的数据同步链路。

## 解决方案

后端划分为用户、文章、评论、点赞、通知、搜索六个限界上下文。每个上下文拥有自己的统一语言、领域模型、业务规则和数据所有权；业务协作优先通过稳定查询契约或集成事件完成。搜索同步是明确例外：Meilisync 只读订阅文章表 ROW Binlog，并把文章表字段作为发布的数据契约，但搜索上下文仍不得引用文章实体、仓储或写入文章数据。

系统继续使用现有 Leo 脚手架，保持 `api → app → domain → repo → clients` 的依赖方向，并以单体方式部署。HTTP、gRPC、Consumer、Job 和运维命令是应用入口或适配器，不额外构成限界上下文。

点赞关系由点赞上下文作为事实源。文章和评论上下文消费点赞事件，维护各自的 `like_count` 查询投影；通知同样通过集成事件异步更新。搜索由 Meilisync 订阅 MySQL ROW Binlog 并同步到 Meilisearch。系统接受短暂延迟；业务事件链路通过事务 Outbox、至少一次投递、幂等消费和定期对账保证可恢复性，搜索链路通过 Redis 同步进度、全量刷新和一致性检查保证可恢复性。

## 用户故事

1. 作为游客，我希望使用唯一昵称、唯一手机号和密码注册，以便拥有博客账号。
2. 作为用户，我希望使用手机号或昵称登录，以便访问需要身份认证的功能。
3. 作为用户，我希望选择记住登录状态和设备类型，以便控制会话有效期并支持多设备登录。
4. 作为用户，我希望退出当前设备，而不影响其他设备的登录状态。
5. 作为用户，我希望查看自己的完整资料和登录信息，以便了解账号状态。
6. 作为访客，我希望查看他人的公开资料，同时看不到手机号、角色等私有信息。
7. 作为用户，我希望修改昵称和头像，以便维护个人资料。
8. 作为用户，我希望先验证旧密码并获得一次性凭证，再修改密码，以降低凭据泄漏风险。
9. 作为用户，我希望修改密码后收敛其他设备会话，以便阻止旧会话继续使用账号。
10. 作为用户，我希望修改手机号，同时保持手机号全局唯一。
11. 作为用户，我希望直接上传头像到对象存储并确认使用，以避免文件经过业务服务器中转。
12. 作为管理员作者，我希望获取正文图片上传凭证，并在 Markdown 中通过稳定图片引用使用它。
13. 作为管理员作者，我希望创建草稿或已发表文章，并原子绑定正文图片。
14. 作为管理员作者，我希望更新文章及其图片引用，同时保持文章和图片关系一致。
15. 作为管理员作者，我希望发布文章，使其对公众可见并进入搜索同步流程。
16. 作为管理员作者，我希望将文章移入垃圾箱，而不是立即删除数据。
17. 作为管理员作者，我希望查看、筛选和分页管理自己的文章。
18. 作为管理员作者，我希望查看文章的可编辑详情、图片映射和互动统计。
19. 作为管理员作者，我希望恢复垃圾箱中的文章为草稿。
20. 作为管理员作者，我希望彻底删除垃圾箱文章及其已绑定对象。
21. 作为访客，我希望分页查看已发表文章并看到摘要和互动统计。
22. 作为访客或登录用户，我希望查看公开文章详情；登录用户还希望看到自己的点赞状态。
23. 作为系统，我希望异步记录浏览事件，以避免统计写入拖慢文章详情响应。
24. 作为登录用户，我希望系统保留我的浏览历史；游客浏览只增加浏览量而不保存历史。
25. 作为访客，我希望查看文章热榜，以发现当前最热门的内容。
26. 作为系统，我希望定时从权威数据重建热榜，以修复缓存漂移。
27. 作为登录用户，我希望发表主评论或回复，并立即获得评论 ID 和创建时间。
28. 作为访客，我希望分页查看主评论和楼中楼回复，并能只看楼主评论。
29. 作为评论作者，我希望删除自己的评论；删除主评论时其回复也不再公开。
30. 作为管理员，我希望删除违规评论，而无需成为评论作者。
31. 作为登录用户，我希望对文章点赞或取消点赞，重复操作仍可安全成功。
32. 作为登录用户，我希望对评论点赞或取消点赞，重复操作仍可安全成功。
33. 作为文章或评论读者，我希望最终看到准确的点赞数，即使计数更新存在短暂延迟。
34. 作为文章作者，我希望他人首次点赞我的文章时收到通知，但自己点赞自己时不产生通知。
35. 作为用户，我希望分页查看通知、查看未读数并一键全部标记为已读。
36. 作为访客，我希望按标题、拼音、标签和正文搜索已发表文章，并看到高亮和摘要。
37. 作为系统，我希望文章发布、更新、删除后最终反映到搜索索引中。
38. 作为运维人员，我希望通过临时索引和 Index Swap 原子重建搜索索引，以避免重建期间中断查询。
39. 作为内部服务，我希望通过 JWT 认证的 gRPC 接口查询用户、文章和评论信息。
40. 作为外部合作方，我希望通过带防重放保护的 HMAC 认证调用公开 gRPC 接口。
41. 作为运维人员，我希望 HTTP、gRPC、Consumer、Job 和管理端点遵循统一生命周期并优雅退出。
42. 作为排障人员，我希望每次请求都具有稳定 Trace ID、统一业务错误和结构化日志。
43. 作为系统维护者，我希望消息重复投递不会导致计数或通知投影重复变化。
44. 作为系统维护者，我希望异步链路失败后能够重试、进入死信队列并通过对账恢复。

## 实现决策

- 系统采用单体部署和六个限界上下文：用户、文章、评论、点赞、通知、搜索。
- 用户上下文拥有用户身份、凭据、角色、资料、手机号和登录会话规则；Redis 会话是该上下文的持久化适配器。
- 文章上下文拥有文章生命周期、正文图片绑定、浏览历史、浏览量、评论数、点赞数投影和热榜投影。
- 评论上下文拥有主评论、回复、删除状态、回复数和点赞数投影；回复统一直属根评论，通过被回复用户标识表达回复对象。
- 点赞上下文拥有文章点赞关系和评论点赞关系，是“谁点赞了什么”的唯一事实源；点赞、取消点赞均为幂等操作。
- 通知上下文拥有通知文档、未读状态和展示快照，只消费集成事件，不反向修改用户、文章或点赞数据。
- 搜索上下文拥有搜索文档、Meilisearch `articles` 索引、Index Settings、查询规则和 Meilisync 转换插件；索引保留全部文章状态，公开查询由后端强制追加 `status = 3`。
- HTTP、开放 gRPC、Consumer、Job、迁移和管理端点属于应用入口或适配器，不作为新的限界上下文。
- 上下文之间通常只传递标识符、稳定 DTO 和版本化集成事件；禁止直接使用其他上下文的实体或仓储接口。搜索同步按功能基线把文章表 ROW Binlog 作为只读发布数据契约，这是唯一允许的跨上下文数据库集成例外。
- 跨上下文事件至少包含事件 ID、事件类型、版本、发生时间、聚合标识和业务载荷；消费者按事件 ID 幂等处理。
- 业务写入与 Outbox 记录处于同一数据库事务；发布器采用至少一次投递。Consumer 失败时重试，超过上限进入死信队列。
- 点赞上下文提交点赞事实后发布事件；文章或评论上下文消费事件维护 `like_count`，因此计数为最终一致投影。
- 评论上下文提交评论事实后发布事件；文章上下文消费事件维护 `comment_count`。浏览事件异步维护浏览历史和 `view_count`。
- 通知上下文消费文章点赞事件创建通知；发送者就是文章作者时忽略。当前只主动生成文章点赞通知，文档中的其他通知类型继续只作存量兼容。
- Meilisync 订阅 MySQL `articles` 表的 INSERT、UPDATE、DELETE ROW Binlog：新增和更新覆盖 Meilisearch 文档，物理删除移除文档；草稿和软删除文章仍保留在索引中，由公开查询的固定状态过滤隐藏。
- 搜索文档包含文章 ID、标题、标题拼音、拼音首字母、纯文本正文、标签、状态和更新时间。拼音、首字母、Markdown 清理和标签规范化由 Meilisync 插件生成，不增加额外 MySQL 字段或搜索同步表。
- 搜索使用固定 `articles` 索引名；全量刷新创建临时索引、复用正式索引设置、分批读取文章全表，并通过 Meilisearch Index Swap 原子交换。刷新前暂停增量同步，检查完成后恢复。
- MySQL 保存用户、文章、评论、点赞、浏览历史、图片关系、Outbox 和必要投影；Redis 保存会话、幂等/Nonce、缓存、热榜及 Meilisync 同步进度；MongoDB 保存通知；MinIO 保存图片；Meilisearch 保存搜索文档；Kafka 承载业务集成事件。
- 对外 HTTP 路由、字段、统一响应结构、认证前缀和业务效果以现有功能文档为兼容基线。文档明确列为“当前未接入”的能力不在本规格中主动接线。
- HTTP 接口继续返回统一 `{success, code, message, data}`，并保留当前固定 HTTP 200 的兼容行为；未来改为语义化 HTTP 状态码应另立兼容性规格。
- 列表接口继续支持当前游标与 Offset 分页规则；每个上下文内部可以复用技术分页组件，但不共享领域模型。
- 对外协议优先在 Proto 中声明，应用服务实现生成的 HTTP/gRPC 接口；不得另建重复 DTO 或手写同义路由。
- 保持 Leo 生命周期、传输、日志、中间件、配置、Actuator、Stream 和 Wire 依赖注入方式。
- 用户、文章等名称在代码中表示限界上下文，不等价于数据库表或单个实体；公共技术组件不得演变为共享领域模型。

## 测试决策

- 测试只验证外部行为、领域不变量和上下文契约，不断言私有函数、目录结构或具体 ORM 调用。
- 同步功能通过 Proto 生成的 HTTP/gRPC 服务接口作为最高层测试接缝；仓储、时钟、随机数、对象存储和事件发布器使用可控替身。
- 业务异步功能通过“发布集成事件 → Consumer 消费 → 本地投影变化”作为测试接缝，覆盖正常、重复、失败重试、死信和乱序场景。搜索同步单独通过“MySQL ROW Binlog → Meilisync 转换 → Meilisearch 文档”作为测试接缝。
- 每个限界上下文测试自己的领域规则、应用接口、持久化契约和事件契约，不通过访问其他上下文数据库完成断言。
- 关键跨上下文链路使用少量真实基础设施集成测试：文章点赞到计数投影与通知、评论创建到文章评论数、文章 ROW Binlog 经 Meilisync 同步到 Meilisearch、文章详情到浏览投影。
- 使用真实 MySQL、Redis、Kafka、MongoDB、MinIO、Meilisearch 和 Meilisync 的测试环境时，测试必须隔离数据并可重复执行。
- 当前仓库没有业务测试先例；首个基础工单需要建立统一测试夹具、假客户端和集成测试启动方式，后续工单复用该接缝。
- 每张实现工单至少包含一个失败测试、一个成功测试和相关幂等/权限/状态边界测试；最终一致链路还必须包含重复消息测试。

## 不在范围内

- 不在本规格中将单体拆成独立微服务或独立部署单元。
- 不新增当前功能文档未定义的产品功能。
- 不主动启用旧密码加新密码直接修改的兼容接口。
- 不主动生成评论点赞、评论文章或回复评论通知。
- 不实现未绑定孤立图片的自动清理任务。
- 不在本规格中改变既有 HTTP 路由、字段、统一响应结构或业务错误语义。
- 不以一次重构同时替换 Leo、Proto、数据库或消息基础设施。

## 补充说明

- 本规格描述目标边界与行为，不固定具体文件路径，避免实现期间目录调整使规格失效。
- 工单应按可独立验收的纵向功能切片执行；不能把一个完整限界上下文的全部能力压入单张工单。
- 推荐先完成基础契约与测试接缝，再按用户、文章、评论、点赞、通知、搜索推进，最后完成开放 gRPC、运维链路和跨上下文验收。
