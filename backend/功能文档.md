# 博客系统现有功能说明

本文档盘点截至 2026 年 9 月 3 日代码中已经实现并接入的功能，作为后续 AI 重构的行为基线。请求流程只描述业务步骤，不绑定当前包、类、方法或分层结构；重构时可以调整内部实现，但应保持文档列出的对外契约和业务效果。

## 通用约定

- HTTP 接口统一返回 `{success, code, message, data}`，HTTP 状态码固定为 `200`，实际结果由 `success` 和业务 `code` 表示。
- 登录接口使用 `Authorization: Bearer <access_token>`；普通登录路由前缀为 `/auth`，管理员路由前缀为 `/admin`。
- 时间字段除特别说明外均为 Unix 秒；IP 字段返回通过 IP 地址库转换后的地区文案。
- 列表接口同时出现 `last_id` 和 `page` 时，`last_id > 0` 使用游标分页，否则使用 Offset 分页。
- 文章状态：`1`-已删除、`2`-草稿、`3`-已发表；用户角色：`1`-普通用户、`2`-管理员。

# MySQL 表结构约束

本节以原项目 `blog-system/blog/scripts/mysql/*.sql` 建表脚本为唯一数据库基线。数据库名固定为 `blog`，字符集为 `utf8mb4`，排序规则为 `utf8mb4_general_ci`。

## 重构约束

- MySQL 只允许存在 `users`、`articles`、`article_images`、`comments`、`article_likes`、`comment_likes`、`article_view_histories` 这 7 张业务表；搜索直接通过 Meilisync 同步 `articles`，禁止为搜索新增投影表、中间表或同步表。
- 未经明确需求和数据库变更确认，禁止新增或删除表、字段、索引、唯一约束、外键和触发器，也不得擅自修改字段类型、长度、空值规则、默认值、状态值或时间语义。
- 当前建表脚本没有声明数据库外键，表间引用完整性由领域逻辑和事务保证；重构时不得自行添加外键或级联规则。
- 数据库时间字段均为 `DATETIME`；对外接口按通用约定转换为 Unix 秒，禁止为了接口格式将数据库字段改成整数时间戳。
- 数据访问模型必须与下列字段一一对应；派生字段、搜索字段和响应展示字段在应用内或 Meilisync 插件中生成，不得据此扩充 MySQL 表结构。

# 用户认证与会话

## 用户注册

**接口**：`POST /user/register`，公开接口。

**请求参数**：JSON Body：`nickname string` 必填且唯一；`phone string` 必填且唯一；`password string` 必填，最少 6 个字符。

**返回参数**：`data=null`，成功消息为“注册成功”。

**请求流程链路**：用户提交昵称、手机号和密码 → 校验请求参数 → 查询手机号或昵称是否已被使用 → 对密码进行单向哈希 → 设置默认头像、普通用户角色、正常状态和注册信息 → 将用户信息写入 MySQL → 返回注册结果。

**技术方案**：Gin + GORM + MySQL；密码使用随机 Salt 的 PBKDF2-SHA256，迭代 100000 次，保存格式为 `pbkdf2$迭代次数$Salt$Hash`。

## 用户登录

**接口**：`POST /user/login`，公开接口。

**请求参数**：JSON Body：`phone string` 和 `nickname string` 至少提供一个；`phone` 只能为数字，`nickname` 不能全为数字；`password string` 必填；`remember_me boolean` 可选；`device string` 可选，如 `web`、`ios`、`android`。

**返回参数**：`data.access_token string`，为 32 字节安全随机数的十六进制字符串；普通会话有效期 7 天，`remember_me=true` 时为 30 天。

**请求流程链路**：用户输入手机号或昵称及密码 → 校验请求参数 → 查询用户是否存在且状态正常 → 对比密码是否正确 → 更新最后登录 IP 和时间 → 生成访问 Token → 将用户、设备和登录信息写入 Redis → 返回访问 Token。

**技术方案**：账号存储使用 MySQL；密码通过 PBKDF2-SHA256 和恒定时间比较校验；登录态使用 Redis 有状态会话，支持同一用户多设备登录。

## 登录身份校验

**接口**：所有 `/auth/*` 和 `/admin/*` HTTP 接口的前置能力。

**请求参数**：Header：`Authorization: Bearer <access_token>`。

**返回参数**：校验成功后继续处理业务请求；缺失、格式错误、过期或不存在时返回未登录或 Token 无效业务码。

**请求流程链路**：读取 Bearer Token → 查询 Redis 会话 → 获取用户 ID 和角色 → 将身份信息传递给后续业务 → 管理员接口继续校验角色是否为管理员。

**技术方案**：Redis Key `auth:token:<token>` 保存会话 JSON，`auth:user-tokens:<userID>` 保存用户的全部 Token；C 端登录态不使用 JWT。

## 退出登录

**接口**：`POST /auth/my/logout`，需要登录。

**请求参数**：无请求体参数，使用当前 Bearer Token。

**返回参数**：`data=null`，成功消息为“退出成功”。

**请求流程链路**：用户携带 Token 请求退出 → 校验 Token 和会话 → 查询 Token 所属用户 → 删除当前 Redis 会话 → 从用户会话集合移除当前 Token → 返回退出结果。

**技术方案**：Redis 会话即时失效，仅退出当前设备，不影响其他设备。

# 用户资料与账号

## 查看个人资料

**接口**：`GET /auth/my/profile`，需要登录。

**请求参数**：无。

**返回参数**：`data` 包含 `id`、`nickname`、`avatar`、`role`、`last_login_time`、`last_login_ip`。

**请求流程链路**：校验登录态 → 获取当前用户 ID → 查询正常状态用户 → 转换最后登录 IP 为地区文案 → 返回完整个人资料。

**技术方案**：MySQL 保存用户资料，IP 地址库负责地区转换。

## 查看他人公开资料

**接口**：`GET /user/profile`，公开接口。

**请求参数**：Query：`user_id uint64` 必填。

**返回参数**：`data` 包含 `id`、`nickname`、`avatar`，不返回手机号、角色和登录信息。

**请求流程链路**：校验用户 ID → 查询正常状态用户 → 过滤私有字段 → 返回公开资料。

**技术方案**：GORM + MySQL，只暴露公开 DTO 字段。

## 修改个人资料

**接口**：`POST /auth/my/profile/update`，需要登录。

**请求参数**：JSON Body：`nickname string` 必填；`avatar string` 可为空。

**返回参数**：`data=null`，成功消息为“个人资料修改成功”。

**请求流程链路**：校验登录态和请求参数 → 查询当前用户 → 修改昵称和头像字段 → 更新 MySQL → 返回修改结果。

**技术方案**：用户领域状态变更 + GORM 持久化；当前接口允许直接提交头像字符串。

## 验证旧密码

**接口**：`POST /auth/my/password/verify`，需要登录。

**请求参数**：JSON Body：`old_password string` 必填。

**返回参数**：`data.change_token string`，一次性改密凭证，有效期 10 分钟。

**请求流程链路**：校验登录态 → 查询当前用户 → 校验旧密码 → 生成一次性随机凭证 → 将凭证和用户 ID 写入 Redis → 返回改密凭证。

**技术方案**：PBKDF2 密码校验；Redis 保存 `user:password-change:<token>`，并设置 10 分钟 TTL。

## 修改密码

**接口**：`POST /auth/my/password/change`，需要登录。

**请求参数**：JSON Body：`change_token string` 必填；`new_password string` 必填且最少 6 个字符。

**返回参数**：`data=null`，成功消息为“密码修改成功”。

**请求流程链路**：校验登录态 → 原子消费一次性改密凭证 → 校验凭证属于当前用户 → 校验并哈希新密码 → 更新 MySQL 密码 → 删除除当前设备外的其他登录会话 → 返回修改结果。

**技术方案**：Redis `GETDEL` 保证凭证只能使用一次；PBKDF2-SHA256 生成新哈希；修改成功后执行多设备会话收敛。

## 修改手机号

**接口**：`POST /auth/my/account/update`，需要登录。

**请求参数**：JSON Body：`phone string` 必填。

**返回参数**：`data=null`，成功消息为“电话修改成功”。

**请求流程链路**：校验登录态和手机号 → 查询当前用户 → 检查手机号是否被其他用户使用 → 更新手机号和更新时间 → 返回修改结果。

**技术方案**：GORM + MySQL，应用校验和数据库唯一索引共同保证手机号唯一。

## 获取头像上传凭证

**接口**：`POST /auth/my/avatar/upload-url`，需要登录。

**请求参数**：JSON Body：`file_ext string` 必填，必须在配置的图片扩展名白名单中。

**返回参数**：`data.upload_url string` 为预签名 PUT 地址；`data.object_key string` 为头像对象 Key。

**请求流程链路**：校验登录态和文件扩展名 → 生成当前用户专属对象 Key → 生成 10 分钟有效的上传地址 → 返回上传凭证。

**技术方案**：MinIO 预签名 PUT；对象路径为 `avatar/<userID>/<UUID>.<ext>`，文件不经过博客服务器中转。

## 确认头像上传

**接口**：`POST /auth/my/avatar/confirm`，需要登录。

**请求参数**：JSON Body：`object_key string` 必填，必须属于当前用户的 `avatar/<userID>/` 路径。

**返回参数**：`data.avatar_url string`，为头像完整公开访问地址。

**请求流程链路**：校验登录态和对象归属 → 查询当前用户 → 将对象 Key 写入头像字段 → 更新 MySQL → 拼接公开访问地址 → 返回头像 URL。

**技术方案**：MySQL 保存对象 Key，MinIO 保存文件，公开域名由配置提供；当前实现不校验对象是否已实际上传，也不自动删除旧头像。

# 文章内容管理

## 获取正文图片上传凭证

**接口**：`POST /admin/article/image/upload-url`，需要管理员权限。

**请求参数**：JSON Body：`file_ext string` 必填，必须在图片扩展名白名单中。

**返回参数**：`data.image_id uint64`、`data.upload_url string`、`data.url string`。

**请求流程链路**：校验管理员身份和扩展名 → 生成按年月组织的对象 Key → 生成 10 分钟有效的 MinIO 上传地址 → 创建未绑定图片记录 → 返回图片 ID、上传地址和预览地址 → 前端上传后在 Markdown 中写入 `image://<image_id>`。

**技术方案**：MinIO 直传 + MySQL `article_images` 表；正文保存稳定图片占位符，预签名 URL 不入库。

## 创建文章

**接口**：`POST /admin/article/create`，需要管理员权限，并启用 2 秒防重复提交。

**请求参数**：JSON Body：`title string` 必填；`content string` 必填，支持 Markdown；`tags []string` 可选；`status int8` 可选，可取 `2` 草稿或 `3` 已发表，未传时当前实现保存为 `0` 兼容状态。

**返回参数**：`data=null`，当前接口不返回新文章 ID。

**请求流程链路**：校验管理员和请求参数 → 创建文章业务对象 → 解析正文中的 `image://<image_id>` → 在同一事务中写入文章并绑定全部未归属图片 → 返回创建结果。

**技术方案**：GORM + MySQL 本地事务；Goldmark 解析 Markdown AST；图片不存在或已属于其他文章时整体回滚。

## 更新文章

**接口**：`POST /admin/article/update`，需要管理员权限。

**请求参数**：JSON Body：`id uint64`、`title string`、`content string` 必填；`tags []string` 可选；`status int8` 可选，可取 `2` 或 `3`，未传时当前实现会按 `0` 保存。

**返回参数**：`data=null`。

**请求流程链路**：校验管理员和请求参数 → 查询文章并校验作者及非删除状态 → 对比新旧正文图片引用 → 在同一事务中绑定新增图片、解绑移除图片并更新文章 → 返回更新结果。

**技术方案**：领域状态校验 + MySQL 事务 + Markdown AST；外部图片 URL 不参与图片关系同步，移除的系统图片只解除绑定，不立即删除对象。

## 发布文章

**接口**：`POST /admin/article/publish`，需要管理员权限。

**请求参数**：JSON Body：`id uint64` 必填。

**返回参数**：`data=null`。

**请求流程链路**：校验管理员和文章 ID → 查询文章 → 校验操作者是作者且文章未删除 → 将状态改为已发表 → 更新 MySQL → 由搜索同步链路异步加入公开搜索索引。

**技术方案**：MySQL `articles` 表保存文章及其状态；Meilisync 监听该表 Binlog 并将状态变化增量同步到 Meilisearch，公开搜索通过 `status = 3` 过滤已发表文章。

**请求流程链路**：校验分页参数 → 仅查询已发表文章 → 根据游标或页码分页并排序 → 统计文章总数 → 截取正文摘要 → 返回列表。

## 公开文章详情

**接口**：`GET /optional/article/detail`，游客和登录用户均可访问。

**技术方案**：可选登录中间件 + MySQL + Redis 点赞缓存 + Kafka 异步浏览事件；浏览事件失败不影响详情响应。

## 浏览历史与浏览量

**请求流程链路**：用户访问文章详情 → 异步发送浏览消息到 Kafka → 消费者解析消息 → 登录用户写入 MySQL 浏览历史 → 增加文章浏览量。

**技术方案**：Kafka 解耦阅读请求与统计写入；MySQL 保存浏览历史及文章浏览数，消费失败按 Kafka 消费策略重试。

**请求流程链路**：从 Redis 读取热度前 10 的文章 ID 和分值 → 批量查询文章标题及统计数据 → 按 Redis 排名顺序组装结果 → 跳过已不存在的文章 → 返回榜单。

## 热榜定时重建

**触发入口**：HTTP 服务启动时执行一次，之后每小时整点执行。

**输入参数**：无外部参数。

**处理结果**：从 MySQL 选取热度最高的 100 篇已发表文章并覆盖 Redis 热榜。

**请求流程链路**：查询已发表文章统计 → 计算每篇文章热度 → 取前 100 篇 → 覆盖写入 Redis Sorted Set → 后续查询读取新榜单。

**技术方案**：Robfig Cron，禁止同一任务重叠执行并捕获 Panic；MySQL 作为权威数据源，Redis 作为查询缓存。

# 文章搜索

## 搜索已发表文章

**接口**：`GET /article/search`，公开接口。

**请求参数**：Query：`keyword string` 必填且去除首尾空格后不能为空；`page uint64` 必填且从 1 开始；`page_size uint64` 必填，取值 10～20。

**返回参数**：`data.list[]` 每项包含 `id`、`title`、`title_highlight`、`summary`、`tags`；同时返回 `total`、`page`、`page_size`。

**请求流程链路**：校验关键词和分页参数 → 调用 Meilisearch `articles` 索引并强制过滤 `status = 3` → 匹配标题、标题拼音、标签、拼音首字母和纯文本正文 → 按相关性分页 → 从 `_formatted.title` 读取标题高亮 → 从 `_formatted.content_plain` 读取裁剪摘要 → 返回搜索结果。

**技术方案**：Meilisearch + Go SDK；将 `status` 配置为 `filterableAttributes`，所有公开搜索必须由后端固定追加 `status = 3`，不得由客户端覆盖；`searchableAttributes` 按 `title`、`title_pinyin`、`tags`、`title_initials`、`content_plain` 排列字段优先级，中文字段使用 `zho` 本地化分词，拼音和纯文本字段由 Meilisync 插件根据 `articles` 原始字段生成，不新增数据库字段；查询通过 `attributesToHighlight` 和 `attributesToCrop` 生成 `<em>` 高亮及正文摘要；搜索不可用时不降级到 MySQL LIKE。

## 搜索索引增量同步

**运行入口**：`meilisync -c configs/meilisync.yml start`，作为独立长期运行进程或容器。

**输入参数**：MySQL `articles` 表的 INSERT、UPDATE、DELETE ROW Binlog 事件；Meilisync 配置包含 MySQL、Meilisearch、同步字段、数据转换插件和 Redis 进度存储。

**处理结果**：文章新增或更新时写入或覆盖 Meilisearch `articles` 索引，物理删除时移除对应文档；索引保留文章状态，公开搜索只返回状态为已发表的文章。

**请求流程链路**：`articles` 表产生 ROW Binlog → Meilisync 读取文章变更 → 插件清理 Markdown、图片占位符和代码内容，规范化标签并生成标题拼音与首字母 → Meilisync 按批量大小或刷新间隔聚合事件 → 调用 Meilisearch 文档新增、更新或删除接口 → 在 Redis 中记录同步进度。

**技术方案**：MySQL `articles` 表 ROW Binlog + Meilisync + Meilisearch；Meilisync 直接承担数据库变更捕获、数据转换、批量写入和同步进度管理。搜索文档包含文章 ID、标题、标题拼音、拼音首字母、纯文本正文、标签、状态和更新时间，不增加额外 MySQL 表。

## 搜索索引全量重建

**运行入口**：`meilisync -c configs/meilisync.yml refresh -t articles`，一次性刷新 Meilisearch 索引。

**输入参数**：无业务参数，直接读取 MySQL `articles` 表以及 Meilisearch、Meilisync 配置；写入批量大小由配置控制。

**处理结果**：日志记录 MySQL 文章数、临时索引和一致性检查结果；刷新失败时线上 `articles` 索引保持不变，成功交换索引后由 Meilisync 清理承载旧数据的临时索引。

**请求流程链路**：暂停 Meilisync 增量进程 → 执行 Meilisync `refresh` → 创建临时 Meilisearch 索引并复制正式索引设置 → 分批读取 MySQL `articles` 全表 → 通过同一插件转换搜索字段并批量导入 → 等待异步任务完成 → 使用 Meilisearch Index Swap 原子交换临时索引与 `articles` 索引 → 执行 `meilisync check -t articles` 核对数量 → 恢复增量同步。

**技术方案**：Meilisearch Index Settings + Meilisync Refresh；配置 `searchableAttributes`、`displayedAttributes`、`filterableAttributes: [status]` 和中文 `localizedAttributes`，使用 Meilisearch 内置中文分词，拼音、首字母和纯文本正文由 Meilisync 插件生成。Meilisync 通过临时索引和 Index Swap 完成原子切换，重建期间搜索客户端始终访问稳定的 `articles` 索引名。

# 开放 gRPC 服务

## gRPC 统一认证

**运行入口**：`blog grpc --port <port>`，默认读取配置端口。

**请求参数**：内部调用携带 Metadata `authorization: Bearer <JWT>`；外部合作方携带 `x-access-key-id`、`x-signature`、`x-timestamp`、`x-nonce`。

**返回参数**：认证成功后执行目标 RPC；失败返回标准 gRPC `Unauthenticated` 等状态码。

**请求流程链路**：根据是否存在 Access Key 选择认证方式 → 内部请求校验 JWT 签名、签发者和过期时间 → 外部请求校验时间窗口、Nonce、防篡改请求体哈希和 HMAC 签名 → 注入调用方身份 → 执行业务查询。

**技术方案**：gRPC Unary Interceptor；内部认证使用 HS256 JWT；外部认证使用 HMAC-SHA256，Redis `SETNX` 保存 60 秒 Nonce 防止重放。

## 查询用户基本信息

**RPC**：`/blogopen.v1.UserService/GetUserBasicInfo`，设计为内部服务调用。

**请求参数**：`user_id uint64`，必须大于 0。

**返回参数**：`user_id`、`nickname`、`avatar`、`last_login_time`、`last_login_ip`。

**请求流程链路**：认证调用方 → 校验用户 ID → 查询正常状态用户 → 转换登录 IP 地区 → 返回用户基本信息。

**技术方案**：Protocol Buffers + gRPC + MySQL。

## 查询用户公开信息

**RPC**：`/blogopen.v1.UserService/GetPublicUserInfo`，设计为外部合作方调用。

**请求参数**：`user_id uint64`，必须大于 0。

**返回参数**：`id`、`avatar`、`nickname`。

**请求流程链路**：认证合作方 → 校验用户 ID → 查询正常状态用户 → 过滤登录信息等私有字段 → 返回公开资料。

**技术方案**：Protocol Buffers + gRPC + HMAC 合作方认证。

## 查询已发表文章列表

**RPC**：`/blogopen.v1.ArticleService/GetAvailableList`。

**请求参数**：`page uint64` 必须大于 0；`page_size uint64` 取值 1～100；`is_desc boolean` 控制排序方向。

**返回参数**：`items[]` 每项包含 `id`、`title`、`tags`、`created_time`、`updated_time`；同时返回 `total`、`page`、`page_size`。

**请求流程链路**：认证调用方 → 校验分页参数 → 查询已发表文章 → 统计总数 → 转换为开放字段 → 返回列表。

**技术方案**：Protocol Buffers + gRPC + GORM/MySQL Offset 分页。

## 查询评论统计

**RPC**：`/blogopen.v1.CommentService/GetCommentStats`。

**请求参数**：`comment_id uint64`，必须大于 0。

**返回参数**：`comment_id`、`hot_value`、`like_count`；当前 `hot_value = 点赞数 + 回复数`。

**请求流程链路**：认证调用方 → 校验评论 ID → 查询评论 → 计算评论热度 → 返回点赞数和热度。

**技术方案**：Protocol Buffers + gRPC + MySQL。

# 后台进程与运维

## Kafka 消费进程

**运行入口**：`blog kafka-consume`。

**输入参数**：配置中的 Kafka Broker、Topic、消费组、批量大小、超时和重试参数。

**处理结果**：消费通知和浏览历史两个 Topic；失败消息按配置重试，最终可写入死信 Topic。

**请求流程链路**：启动独立消费进程 → 为通知和浏览历史注册处理器 → 分 Topic 批量拉取消息 → 执行业务写入 → 成功后提交位点 → 失败时重试或进入死信队列 → 收到退出信号后优雅停止。

**技术方案**：Kafka Consumer Group + 批量消费 + 重试 + Dead Letter Queue；通知落 MongoDB，浏览历史和计数落 MySQL。

## 数据库初始化

**运行入口**：`blog migrate`。

**输入参数**：读取 `config/config.yaml` 的 MySQL 配置和 `scripts/mysql` 目录中的 SQL 文件。

**处理结果**：创建博客数据库，并执行用户、文章、文章图片、评论、点赞和浏览历史等建表脚本。

**请求流程链路**：连接 MySQL → 执行建库脚本 → 切换到目标数据库 → 扫描 SQL 文件 → 按文件逐条执行 SQL → 输出初始化结果。

**技术方案**：Go `database/sql` + MySQL Driver；当前实现按分号拆分 SQL，不提供版本化迁移、回滚和迁移记录表。

## HTTP 服务启动

**运行入口**：`blog server --port <port>`，默认端口 8080。

**输入参数**：配置文件及可选监听端口。

**处理结果**：启动全部 HTTP 路由、认证和错误中间件、Kafka Producer、热榜初始化及定时任务。

**请求流程链路**：加载配置和参数校验器 → 初始化 MySQL、MongoDB、Redis、Kafka、MinIO 和 Meilisearch 客户端 → 组装业务能力 → 初始化热榜 → 启动定时任务 → 注册路由 → 监听 HTTP 端口；Meilisync 作为独立进程部署，不进入博客 HTTP 服务生命周期。

**技术方案**：Cobra + Gin；基础设施按组合根统一装配，进程退出时关闭已初始化资源。

## 统一错误与请求日志

**触发入口**：所有 HTTP 请求。

**输入参数**：请求方法、路径、Query、Body、Header、处理错误和耗时。

**处理结果**：响应中写入或透传 `X-Trace-ID`；业务错误转换为稳定业务码；记录请求日志。

**请求流程链路**：接收请求 → 生成链路 ID 并记录请求信息 → 执行业务和路由中间件 → 捕获最后一个业务错误 → 映射业务码 → 返回统一响应并记录耗时。

**技术方案**：Gin 全局中间件；统一错误码按请求、用户、Token、文章、评论、Redis、Kafka和搜索模块分段。
